# 0037: A dispatcher's fan-out dilutes its folder-proximity bonus the same way a shared dependency's fan-in does

[Back to documentation/adr/README.md](README.md) • [Back to LLD.md](../LLD.md)

## Status

Accepted. Closes the residual case documentation/adr/0036 left open, applying the same dilution symmetrically to the other side of an edge.

## Context

documentation/adr/0036 diluted a cross-directory edge's folder-proximity bonus by its *target*'s fan-in - how many distinct outside directories import that file - so a file reused identically by several sibling directories (`tree-sitter-common/`) stopped arbitrarily merging into whichever one of them Louvain's tie-breaking favored. It left one smaller case open: `src/extraction/composite-parser.ts` still rode along with whichever single language's Module ended up next to it, varying by file order across the same seven-permutation test used throughout this investigation.

The graph explains why. `src/extraction/parser.ts` (the `Parser` interface) has high fan-in exactly as documentation/adr/0036 anticipates - imported from `tree-sitter-go/`, `-java/`, `-python/`, `-rust/`, and `ts-compiler-api/` alike - so every one of *those* edges is already diluted. But `parser.ts`'s strongest connection isn't any of those: it's `composite-parser.ts` and `parser-factory.ts`, both of which sit in the same directory as `parser.ts` itself (`src/extraction/`, no subdirectory), so their edges to it are same-directory and never diluted by anything. That trio forms its own small, well-anchored cluster. What pulls it toward one specific language is `parser-factory.ts`'s own fan-*out*: it imports one concrete parser file from each of the five language directories, each such edge undiluted because each *target* (e.g. `go-parser.ts`) has a fan-in of exactly one (only `parser-factory.ts` imports it from outside `tree-sitter-go/`). Five equally-weighted edges to five structurally-equivalent siblings is the same tie documentation/adr/0036 fixed, just seen from the dispatcher's side of the edge instead of the shared dependency's side.

## Decision

`externalDirFanCounts` (`src/clustering/louvain/louvain-module-detector.ts`, replacing documentation/adr/0036's `externalImporterDirCounts`) computes both directions in one pass: `fanIn` (distinct external directories importing a file, as before) and `fanOut` (distinct external directories a file imports from). `importEdgeWeight` dilutes by `Math.max(fanIn, fanOut)` for whichever endpoint of the edge is more widely connected, rather than fan-in alone. A file that's both someone's single private dependency *and* itself a hub doesn't get to keep an undiluted weight just because one side of it looks exclusive. Same-directory edges and edges where both counts are `<= 1` are unaffected, exactly as before.

## Consequences

- Measured on this repo's own generated map: `composite-parser.ts`, `parser.ts`, and `parser-factory.ts` now form their own Module (`extraction`), distinct from every language, in all seven of the same file-order permutations used to verify documentation/adr/0036 (previously: distinct from every language in zero of seven - some single language always rode along). Every one of go/java/python/rust/common also stays mutually distinct in all seven runs, confirming the separation is a stable property of the graph, not a new coincidence.
- The same symmetric treatment had a wider reach than this one case: `src/core/cache/` (`cache-schema.ts` + `extraction-cache.ts`) split out of the main `core` Module into its own, because its only link to the rest of core is `generate-map.ts` - the pipeline orchestrator, which fans out to many other directories for unrelated reasons and had that edge diluted along with the rest. Separately, `src/output/json/`'s two files now merge with `clustering/` instead of standing alone, because `build-map-json.ts` directly depends on `clustering/module-naming.ts`'s `deriveModuleNames` and that bridge wasn't diluted as much as `output/json/`'s previous anchor to `output/html/` via the shared `Transformer` interface (itself a fan-in case documentation/adr/0036 already discounts). Both splits were checked for stability the same way as the headline fix: re-run across the same seven file-order permutations, both landed in the same shape every time - real, repeatable consequences of a more symmetric weighting function, not new instances of the instability this and documentation/adr/0036 exist to remove.
- Total unassigned files on this repo's own map moved from 8 to 9, and the Module count from 13 to 15 - more, smaller, more homogeneous Modules, consistent with the trend documentation/adr/0036 started. Every detected Module still gets a real, non-ordinal name.
- `louvain-module-detector.test.ts` gained a test with a dispatcher importing one file from each of three sibling directories (each target privately used, fan-in 1, so documentation/adr/0036 alone wouldn't dilute those edges) plus a same-directory anchor file for the dispatcher to belong to instead - the synthetic analogue of `parser-factory.ts` + `parser.ts` above. All prior tests, including documentation/adr/0036's, passed unchanged.
- No further residual instability of this shape is known. A future case combining high fan-in *and* high fan-out on the same file at values that individually clear the dilution floor but combine to re-create a tie is conceivable but unobserved in this codebase; revisit `Math.max` versus a stronger combination (e.g. multiplying the two counts) if one surfaces.
