# 0036: A shared dependency's fan-in dilutes its folder-proximity bonus

[Back to documentation/adr/README.md](README.md) • [Back to LLD.md](../LLD.md)

## Status

Accepted. Narrows documentation/adr/0007's folder-proximity weighting, on the same weighted-edge mechanism documentation/adr/0014 and documentation/adr/0015 already tune.

## Context

This repo's own `src/extraction/` has one real shared-kernel directory, `tree-sitter-common/`, and four sibling directories that each depend on it identically: `tree-sitter-go/`, `tree-sitter-java/`, `tree-sitter-python/`, `tree-sitter-rust/`. Every one of the four has exactly the same six file-level import edges into the same five `tree-sitter-common/` files, at the same folder-proximity weight (one shared segment, `extraction/`, weight `3^1 = 3`... narrowed to `3^2 = 9` once `fixtures/`/`documentation/` are excluded from the scan and the universal root strips down to `src/`). Running the generator on this repo surfaced a Module whose files mixed `tree-sitter-common/` with exactly one of the four languages - never zero, never more than one.

Rebuilding the real import graph from a generated `codemap.json` and re-running the exact same Louvain call with the file list in seven different (but equally valid) orders showed which language merged with `tree-sitter-common/` changing on almost every run - common merged with go in two runs, java in three, python in two. Rust alone stayed separate in all seven, because it genuinely has more internal edges (8 vs. 5 for the other three) than the others - a real structural fact. The other three are structurally identical with respect to common, so which one "wins" it is tie-breaking noise in Louvain's greedy local-moving heuristic, not a signal about the code.

The arithmetic explains why the partition is so unstable: `tree-sitter-common/`'s own internal cohesion (6 edges x weight 27 = 162, same-leaf-directory edges at full shared depth) very nearly balances the *combined* pull of its three symmetric clients (3 x 6 edges x weight 9 = 162). A near-exact tie in modularity terms has no decisive winner, so whichever client the greedy algorithm happens to visit favourably first keeps it.

documentation/adr/0007's folder-proximity weighting assumes directory adjacency is itself evidence of domain relatedness. That assumption holds for a file privately used by one neighbouring directory (e.g. `compose.ts` wiring into `composite-parser.ts`, documentation/adr/0014's worked example) but not for a file reused the same way by several sibling directories at once - being pulled on identically by N siblings is evidence the file is a shared dependency of all of them, not a member of whichever one a tie-breaking heuristic happens to land it in.

## Decision

A cross-directory import edge's folder-proximity weight is divided by its target's fan-in: the number of distinct *outside* directories that import that file (`externalImporterDirCounts`, `src/clustering/louvain/louvain-module-detector.ts`). Two files in the same external directory importing the same target count once, not twice - it's the number of separate places pulling on the file that matters, not the raw edge count. The discount never drops a weight below the pre-documentation/adr/0007 unweighted floor of 1, and it's skipped entirely for a same-directory edge (full shared depth - internal cohesion, not external fan-out) or a target with only one external importer (`fanIn <= 1`, the common case: most cross-directory edges in this codebase bridge exactly one pair of directories, e.g. `output/html/` and `output/json/`, or a composition root's single wiring edge).

`weightedDegree`'s embeddedness check (documentation/adr/0014) already reads whatever weight is on the edge, so this slots into the existing mechanism with no separate change needed there - the same weighted view drives both community detection and the embeddedness gate, as documentation/adr/0014 established.

## Consequences

- Measured on this repo's own generated map (`fixtures/`/`documentation/` excluded per `codemap.config.json`): `tree-sitter-common/` is now its own Module, separate from every language it serves, in every one of the same seven file-order permutations tested before this decision (previously: separate in zero of seven). Modularity on that reconstructed graph rose from ~0.71 to ~0.81 across all seven orderings - a more decisive partition, not a coincidentally nicer-looking one.
- The same mechanism, applied to `src/core/` - imported from far more than two sibling directories - split one previously-merged Module apart: `core+graph-building` is now two clean Modules, `core` and `graph-building`. Two other core-adjacent Modules stayed merged (`clustering+core`, via `test-file.ts`; `discovery+core`, via the TOML-parsing helpers) - not because their bridge files have a low fan-in (`test-file.ts` is actually imported from three external directories: `clustering/`, `discovery/filesystem/`, and `extraction/tree-sitter-go/`, all diluted alike), but because the raw edge count surviving that dilution is still uneven: two `clustering/` files import `test-file.ts` against one each from the other two, and that asymmetry is real signal, not folder-proximity noise.
- Total unassigned files on this repo's own map dropped from 11 to 8, and every one of the 13 detected Modules still gets a real, non-ordinal name (documentation/adr/0009, documentation/adr/0035) - no naming-layer change was needed; the naming tiers already handle however Louvain partitions the graph.
- `louvain-module-detector.test.ts` gained a test with three symmetric sibling directories sharing a two-file common directory, asserting common stays in its own community and every sibling stays distinct from the others and from common - the synthetic analogue of the `tree-sitter-common` case above. All prior tests passed unchanged: every existing fixture's cross-directory edges have a fan-in of 1 (a single bridging pair), which this decision never discounts.
- A smaller, residual instability remained: `composite-parser.ts` (and the shared `parser.ts` interface it implements alongside every language parser) still rode along with whichever one language's Module ended up adjacent to it, which language that was still varying by file order. This was the dual case in the opposite direction - a dispatcher (`parser-factory.ts`) fanning *out* to one file in each of several sibling directories, rather than a file fanned *into* by several siblings - and is closed by documentation/adr/0037.
