# 0015: The minimum community size is 2, not 3

[Back to 0014-weighted-embeddedness.md](0014-weighted-embeddedness.md) • [Back to documentation/adr/README.md](README.md) • [Back to LLD.md](../LLD.md)

## Status

Accepted. Narrows the `MIN_COMMUNITY_SIZE` threshold fixed by documentation/adr/0001, on top of documentation/adr/0014's weighted-embeddedness fix.

## Context

After documentation/adr/0014 fixed embeddedness to use the same folder-proximity-weighted edges as community detection, this codebase's own generated map still left `src/integration/cli/{main,cli-adapter}.ts` and `src/integration/skill/{main,skill-adapter}.ts` unassigned - not for low embeddedness (both pairs are, in fact, fully embedded in each other, ratio 1.0 - each file's only import edge is to its one sibling), but `undersized`: Louvain correctly detected each pair as its own distinct, folder-cohesive community, but `MIN_COMMUNITY_SIZE = 3` discarded both for having only 2 members. Meanwhile the analogous `src/integration/mcp/` folder has 3 files (`main.ts`, `mcp-adapter.ts`, `server.ts`) and cleared the floor untouched - an accident of that folder happening to have one more file, not a meaningful difference in how real each domain is. A tiny integration surface (an entrypoint plus its one adapter) is exactly the kind of small-but-genuine bounded context `CONTEXT.md`'s Module section already allows for.

Investigating what a size-1 community would even mean surfaced a sizing problem with the constant itself: a community can never have size 0 for a file with degree > 0 (Louvain always assigns every graph node to *some* community, itself at minimum), so `MIN_COMMUNITY_SIZE = 1` would never exclude anything - a floor that low makes the `undersized` classification dead code. Testing `graphology-communities-louvain` directly (several constructed graphs: a lone node weakly bridging one giant community, weakly bridging two roughly-equal giant communities) never produced a true size-1 community for any node with degree > 0 - the local-moving phase always found some community, even a brand-new 2-member one carved out of a larger one, preferable to leaving a connected node alone. So in practice, under this library, `MIN_COMMUNITY_SIZE = 2` and `MIN_COMMUNITY_SIZE = 1` behave close to identically for any non-isolated file; 2 is chosen anyway as the smallest floor that's still logically meaningful (it excludes a genuine singleton community, should one ever occur), consistent with this codebase's pattern of keeping a defensive check even where it's expected to rarely or never fire (e.g. `filesystem-discovery.ts`'s `packageId as string`).

## Decision

`MIN_COMMUNITY_SIZE` (`src/clustering/louvain/louvain-module-detector.ts`) changes from `3` to `2`. `MIN_EMBEDDEDNESS` and `MIN_MODULARITY` are unchanged, and the classification order (isolated → undersized → low-embeddedness → degenerate-partition → assigned) is unchanged - this only moves where the second gate sits.

One classification-order consequence falls out of this directly, not something separately tuned: a 2-file community whose only structure is a single edge between the two files (e.g. a two-file fixture, or a real two-package monorepo with one importing the other) now clears the size floor and reaches the *next* gate, `wholeGraphIsDegenerate` - and a graph that small has no real community structure to speak of (modularity below `MIN_MODULARITY`), so it now correctly comes out `degenerate-partition` instead of `undersized`. That's a more accurate reason than before: the real problem in that case was never community size, it was that there wasn't enough graph to detect a partition from at all.

## Consequences

- Running the generator on its own codebase: unassigned files dropped from 6 (after documentation/adr/0014) to 2. `cli-adapter.ts`/`main.ts` and `skill-adapter.ts`/`main.ts` are now assigned to their own communities. Naming's existing top-level-collision fallback (documentation/adr/0013) then does the rest for free: all three `src/integration/*` communities (`cli`, `mcp`, `skill`) now land on the same top-level name `integration` and fall back to their deeper, already-distinguishing names - so the map now shows `cli`, `mcp`, and `skill` as three separate Modules instead of one `integration` Module (mcp) plus two unassigned pairs. No naming logic changed to produce this; it's the direct, expected consequence of documentation/adr/0012 and documentation/adr/0013 once all three communities exist to collide with each other.
- Two golden fixtures (`fixtures/expected/multi-package-monorepo.codemap.json`, `fixtures/expected/ambiguous-call.codemap.json`) each contained a 2-file, single-edge scenario that was previously `undersized`; both now correctly read `degenerate-partition` per the classification-order consequence above, and were updated to match.
- `louvain-module-detector.test.ts`'s prior "2-file community below the size-3 floor" test encoded the exact case this decision changes; it's now a positive-case test asserting that a fully-embedded 2-file community is assigned, not excluded. No test was added for `undersized` under the new floor - only a genuine size-1 community would trigger it, and empirically this library doesn't appear to produce one for any connected node, so no natural fixture was found to exercise it. The classification itself is left in place as a defensive floor, not removed, per this ADR's Context.
- This raises (slightly) the chance a truly coincidental 2-file pair - two files that happen to import each other with no other connections anywhere in the graph - surfaces as its own tiny Module rather than staying unassigned. Accepted: such a pair is, by construction, 100% mutually embedded (their one edge is each file's only edge), which in practice means a real, deliberate one-to-one relationship (an interface and its sole implementation, an entrypoint and its handler) far more often than an accidental one - and a real folder-derived name for it beats leaving it out of the map entirely.
