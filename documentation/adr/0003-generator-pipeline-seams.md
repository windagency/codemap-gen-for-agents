# 0003: Generator pipeline seams - Factory, GraphBuilder, ModuleDetector, Transformer, and three peer Adapters

[Back to 0029-json-envelope-warnings-field.md](0029-json-envelope-warnings-field.md) • [Back to documentation/adr/README.md](README.md) • [Back to HLD.md](../HLD.md) • [Back to TESTING.md](../TESTING.md)

## Status

Accepted. `Parser`'s interface amended by ADR-0005 (adds an `extractFiles` parameter for incremental extraction; whole-program `programFiles` semantics unchanged). Amended again by `codemap-extraction-algorithm`'s File & Package discovery ticket: adds a fifth `Discovery` seam ahead of `Parser`, and `GraphBuilder.build` gains a second `structure: DiscoveredStructure` parameter. Amended again by that same map's ExtractedSymbols shape & AST-walk classification ticket: `Parser` performs all checker-dependent import/call resolution internally (only it ever holds a `ts.Program`), emitting already-resolved raw refs; `GraphBuilder` is correspondingly narrowed to a pure shape-assembler with no TS-specific logic of its own. Amended again by that same map's Import resolution, re-export handling & External nodes ticket: `Parser.parse` gains a leading `rootDir: string` parameter, used to locate `<rootDir>/tsconfig.json`.

## Context

The map's Notes called for Gang-of-Four-inspired seams (Factory for parser selection, Adapter for per-tool integration surfaces, Transformer/Strategy for output formats) without fixing where exactly they cut. ADR-0002 chose the TypeScript Compiler API for this milestone's extraction layer but explicitly deferred designing the parser Factory seam itself to this decision, since ADR-0002 only fixed *which* parser ships, not the extension point future languages would register through.

Two complications surfaced while designing the seams:

- CODING_RULES/04-architecture.md already mandates its own, narrower "Adapter" pattern: any third-party library with real footprint (here, `graphology-communities-louvain`, chosen in ticket 01) sits behind an interface this codebase owns. That is a different reason for a seam (isolating a library) than the map's Notes' "Adapter" (letting the MCP server and the Skill each drive the same core use-case). Using "Adapter" for both would overload one name for two unrelated seams.
- The TypeScript Compiler API's type-checked call resolution (the reason ADR-0002 chose it over tree-sitter) only works across files if the whole file set is loaded into one `ts.Program` - a strictly per-file parser interface cannot resolve a cross-file call through the type checker at all.

## Decision

The pipeline is a chain of four typed stages - `ExtractedSymbols[]` (per file) → `RawGraph` → `ClusteredGraph`, consumed by output Transformers - with four seams and three peer integration adapters:

- **`Parser` is whole-program, not per-file**: `parse(programFiles: string[], extractFiles: string[]): ExtractedSymbols[]` builds one `ts.Program` over `programFiles` internally and extracts only `extractFiles` against it in a single call, preserving type-checked cross-file call resolution while letting incremental extraction (ADR-0005) skip unchanged files. `ParserFactory.createParser(language: Language)` selects the implementation; this milestone registers exactly one (`TsCompilerApiParser`). The AST itself never crosses this seam - `ExtractedSymbols` is the only type that leaves a `Parser`. **`Parser` also performs all checker-dependent resolution** (import-target and call-target resolution) internally, since it's the only seam that ever holds the `ts.Program`/`ts.TypeChecker` - `ExtractedSymbols` carries already-resolved raw import/call refs (file path, external package name, or candidate callee declarations), not raw AST nodes.
- **`GraphBuilder` is its own registered seam**, not a fixed core step and not bundled with `Parser` under a shared "language plugin" key - its eventual selection axis (if one is ever needed) isn't assumed to track language. `GraphBuilderFactory.create(): GraphBuilder` takes no selection parameter yet; this milestone registers one default implementation, and a parameter is added only when a second implementation actually needs differentiating. `build(symbols: ExtractedSymbols[], structure: DiscoveredStructure): RawGraph` takes a second parameter (added by the `Discovery` seam below) so it stays a pure function of two already-known inputs, with no filesystem or checker access of its own - it only assembles already-resolved raw refs into final schema-id'd nodes/edges (merging same-target entries, fanning out ambiguous-dispatch candidates, creating `ExternalNode`s via the lockfile-resolution seam).
- **`Discovery` is a fifth seam, directly injected like `ModuleDetector`** (no Factory, single implementation): `discover(rootDir: string, exclude: string[]): DiscoveredStructure` walks the repo once per `generate` call, ahead of `Parser`, producing the complete matched-file list (`Parser`'s `programFiles`) and the `Package`/`Directory` structure `GraphBuilder` needs. Every `package.json` found (root manifest included, workspace-declared or not) is its own Package; a file's Package is its nearest ancestor manifest, so Package never nests, matching the Cluster hierarchy. Directory nodes are lazily materialized (only directories with a descendant File). Not cached between runs - it's a cheap walk, and boundaries can shift even when no file's content changed.
- **`ModuleDetector`** wraps `graphology-communities-louvain` (per ticket 01) behind a directly-injected interface, with no Factory - it exists solely to satisfy CODING_RULES/04's library-isolation rule, and is deliberately never called an "Adapter," to keep that word reserved for the tool-integration sense below.
- **`Transformer.transform(graph: ClusteredGraph, options?: TransformOptions): string`** covers both JSON and HTML output. The optional `options` parameter exists so ticket 02's HTML visualization design can add generation-time parameters without renegotiating this interface; ticket 02 works entirely inside `HtmlTransformer`'s implementation.
- **"Adapter" is reserved for the three tool-integration seams**: `CliAdapter`, `McpAdapter`, and `SkillAdapter`. All three are peers - each depends only on a single composition root, `core/compose.ts`'s `createDefaultPipeline()`, in-process. This includes `SkillAdapter`, which calls the core pipeline directly rather than delegating to `CliAdapter`/`McpAdapter` - correcting this same ticket's own original framing, which had assumed the Skill might just be prose instructing an agent to invoke the CLI or MCP tools.

Folders are organized as vertical feature slices (`extraction/`, `graph-building/`, `clustering/`, `output/`, `integration/`), each owning its seam's interface plus implementation subfolder(s), rather than one folder per architectural layer. The `arch-unit-ts` dependency-direction rule: `core/` never imports an implementation subfolder, only each slice's top-level interface/factory file; `integration/*` never imports `extraction/`, `graph-building/`, `clustering/`, or `output/` directly - only `core/`.

## Consequences

- Ticket 05 (public interface contract) must design the Skill's contract as its own adapter surface over the shared core, not as documentation routing an agent between the CLI and MCP tools.
- Ticket 06 (incremental caching) slots into `core/` or `extraction/`, not into any of the four seams directly, since caching concerns which `ExtractedSymbols` need recomputing, upstream of `GraphBuilder`/`ModuleDetector`/`Transformer`.
- `Discovery`'s output is the one piece of structural information (`Package`/`Directory` boundaries) that doesn't originate from `Parser`/`ExtractedSymbols` at all - it's computed directly from the filesystem, independently of any file's content, which is why it needed its own seam rather than being folded into `ExtractedSymbols`.
- The `arch-unit-ts` dependency-direction rule above becomes mandatory test coverage per CODING_RULES/04 - an architecture rule without a matching test isn't enforced.
- `GraphBuilder` and `ModuleDetector` currently each have exactly one implementation and no real second use case; this is accepted as intentional seam design for future language/algorithm support, not speculative over-engineering, since ADR-0002 explicitly named the multi-language future as the reason the parser seam needed real design now rather than later.
- **A file with syntactic diagnostics is skipped, not fatal.** Unparseable/invalid file policy: a file with genuine syntax errors (not mere type errors - those still extract normally) produces no `FileNode` at all, and `Parser` treats any other file's import resolving to it exactly like an unresolved specifier, never a dangling edge target. The run always succeeds; skips are deterministic (reproducible per milestone's golden-file requirement), just not zero. Skips are surfaced both as `GeneratedMap.warnings` (logged by `codemap-public-interface`'s CLI/MCP commands) and, as of [ADR-0029](0029-json-envelope-warnings-field.md), inside `codemap.json`'s own `warnings` field.
- **External version resolution reads the already-installed `package.json`, never a lockfile.** External node & lockfile version resolution design: since an import only becomes `External` after resolving somewhere under an installed `node_modules` (a precondition this ADR already records), `Parser` walks upward from that exact resolved path to the nearest `package.json` with a matching `"name"` and reads its `"version"` - no lockfile-parsing library needed, and no special-casing for git-/`link:`-referenced dependencies (they carry a normal installed `package.json` too). `Parser` resolves this immediately alongside import classification (memoized per resolved package directory); `GraphBuilder` still never touches the filesystem.
- **Ambiguous call-dispatch candidates are nominal-only.** Call resolution enumerates concrete implementations of an interface/abstract method call only via `implements`/`extends` heritage clauses (matched by method name, transitively, ignoring generics) - never true structural ("duck-typed") matching. A class that happens to have a compatible method without declaring `implements` never appears as a candidate. Accepted because whole-program structural matching would mean checking every class against every interface's shape, with real risk of false positives from coincidentally-shaped unrelated classes.
- **One `tsconfig.json` for the whole repo.** Since `Parser` builds exactly one `ts.Program` (this ADR's whole-program decision), it also resolves exactly one `CompilerOptions` set, read from `<rootDir>/tsconfig.json` only (`codemap-extraction-algorithm`'s Import & re-export resolution ticket) - never a workspace member's own `tsconfig.json`, even when one exists and diverges from the root. A package with genuinely different settings (`target`/`lib`/`jsx`) may extract slightly imprecisely; accepted as a real limitation of the whole-program design, not an oversight. `Parser` also requires the analyzed repo's `node_modules` to already be installed to correctly distinguish a genuine external dependency from a broken/unresolvable import - inherited from choosing the TS Compiler API's type-checked resolution over a heuristic parser.
- "Adapter" now has exactly one meaning in this codebase's vocabulary (tool-integration, driving); any future third-party-library wrapper should follow `ModuleDetector`'s naming pattern (a domain-named interface), never "Adapter."

## Update: `node_modules` precondition relaxed

ADR-0032 adds a fallback: an npm import with nothing installed resolves to the declared version in `package.json`. An installed package still always wins, so the precondition now governs fidelity (exact installed version, calls into the package) rather than whether an External node appears at all.
