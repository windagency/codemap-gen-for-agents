Domain glossary for the code-map generator. This file defines terms only - no implementation details, no architecture decisions. See `documentation/adr/` for those.

## Cluster

A node in the navigable structural hierarchy of a mapped codebase. Cluster types nest strictly, each one containing the next:

**Package** ⊃ **Directory** (zero or more, arbitrarily nested) ⊃ **File** ⊃ **Symbol**

- **Package**: one per recognized project manifest found in the mapped repo (`package.json`, `go.mod`, `Cargo.toml` - including each `[workspace]` member as its own additional Package - a Maven/Gradle project file, or a `pyproject.toml` carrying a PEP 621 `[project]` table) - a monorepo's workspace member, or the workspace root's own manifest, whichever contains the file. A directory hosting more than one manifest kind (e.g. a Go service with a co-located Node tooling package) produces one Package per manifest, never a single directory forced to be single-language; those co-located Packages are told apart by a family suffix on their id (`.@go`, `.@npm`), while a directory with one manifest keeps its plain path as its id (`documentation/adr/0034`). A root manifest that only lists `workspaces`/is a pure virtual `[workspace]` and holds no source files of its own is simply an empty Package, no different from any other Package with no files at its own level before nested Directories. A Poetry-only `pyproject.toml` (a `[tool.poetry]` table with no `[project]` table), `setup.py`, `setup.cfg`, and a bare `requirements.txt` are none of them recognized manifests (`documentation/adr/0030`) - files beneath them are manifest-less, the same as any other unmanaged file.
- **Directory**: any filesystem directory between a package root and a file. Nesting is arbitrary depth; a package may have zero directory levels (files directly at its root) or many.
- **File**: a source file. Leaf container of the structural tree, and the level the original ask calls out explicitly: "each file is a cluster comprising its functions, methods, constants."
- **Symbol**: a function, method, class, constant, type, or similar unit extracted from a file. Leaf of the hierarchy - a symbol contains no further clusters.

The structural tree answers "where does this code live on disk." It says nothing about which domain it belongs to - that's Module.

## External

A graph node representing a dependency outside the mapped codebase (an npm/Go-module/Cargo-crate/Maven-or-Gradle/PyPI dependency), used only as the target of an Interaction leaving the codebase (e.g. an import of a third-party package). **Not a Cluster** - it sits outside the structural hierarchy entirely, since that hierarchy only describes code the generator actually walked and parsed. An External node is a lightweight stub carrying its own ecosystem-native coordinate and version: no internal structure, no Symbols, no further nesting. The version is always present by construction - an External node with no version is never produced. For npm it is the installed package's exact version, or, when nothing is installed, the range declared in `package.json` (`documentation/adr/0032`); for Rust and Python it is the declared requirement. For npm/Go/Rust, "name" means the resolved dependency's own manifest-declared identity - never a locally-declared import alias (e.g. an npm-aliased dependency, `"foo": "npm:bar@1.0.0"`, is named `bar`, not `foo`; two different local aliases resolving to the same installed package are therefore one and the same External node, `documentation/adr/0024`). For Java, "name" is the compound `group:artifact` coordinate, not a bare artifact name - two different groups can legitimately publish the same artifact name, so the group is load-bearing. For Python, "name" is the PyPI distribution name declared in `pyproject.toml`'s `dependencies`, matched against an import statement's top-level segment by normalized-name comparison only - an import name that genuinely differs from its distribution name (PyPI `Pillow` imports as `PIL`) is a documented, unresolved gap, not a guess (`documentation/adr/0030`). See [`documentation/LLD.md`'s Parser seam section](documentation/LLD.md#srcextractionts-compiler-api--the-parser-seam) for exactly how a TS/JS version is resolved.

## Module (Domain)

A flat, Domain-Driven-Design-inspired grouping of files by domain/bounded context. **Not a node in the structural tree** - it is a separate, cross-cutting label attached to a File (and, by extension, to that file's symbols). A Module is computed, not declared: it is the deterministic output of a graph-clustering algorithm (community detection) run over the codebase's static import/dependency graph. No config file, no human declaration, and no LLM call are involved in detecting a Module - the same input code must produce the same grouping on every run.

Boundaries:
- A Module frequently coincides with a Directory, and for a well-organized codebase expect most Modules to map onto exactly one Directory. A strong enough import signal can still pull a Module's files across multiple directories - but every file in one exact directory almost always ends up in the same Module: the algorithm merges a directory's minority files into whichever Module already holds a genuine majority of that directory, even when those minority files are individually more tightly coupled to an outside directory than to their own siblings (`documentation/adr/0038`). A directory with no real majority at all - its files split exactly evenly between two or more Modules - is left unreconciled only when the tied sides are genuine individuals (one file each); a tie between two or more substantial, already-cohesive groups is still resolved, deterministically, since picking one over the other doesn't strip anything of a real pairing the way forcing two lone individuals together would (`documentation/adr/0040`, narrowed by `documentation/adr/0053`).
- A Module that scatters across more directories than a small, readable handful is re-examined on its own terms before anything else: community-detection's modularity objective has a well-documented "resolution limit" - in a large enough codebase, two or more genuinely separate domains can look like one Module purely because the whole repo is large enough to make the merge look modularity-positive, even though each domain is exactly as internally cohesive as any other, cleanly-detected Module. Re-running the same detection algorithm on just that Module's own files and internal edges, with the rest of the repo's distorting mass removed, recovers the real boundaries when they exist (`documentation/adr/0051`) - but only when there's real breadth to split along; a small, already single-directory Module has nothing to gain from this and measurably loses from it, so it's never attempted there.
- A Module never spans more than one Package, even when a real import edge connects them (e.g. one package's integration shim importing another's public API) - a Package is a stronger version of the same boundary a Directory already is (manifest-declared and independently versioned, not just a filesystem convention), so a Module that would otherwise straddle two Packages is split along Package lines instead, each Package's own slice becoming its own Module (or going unassigned, if too small on its own) (`documentation/adr/0049`).
- Modules do not nest. There is no "sub-module" or "domain within a domain" - a Module is a single flat label per file, matching the DDD bounded-context idea of a boundary, not a fractal hierarchy.
- A file may end up with no Module label at all, if the clustering algorithm finds it too disconnected from any group to place with confidence. Unassigned is a valid, expected state - the algorithm never forces a low-confidence file into the nearest cluster.
- Every test file (by each language's own convention: for TS/JS, `*.test.*`/`*.spec.*` or any file under a `test/`, `tests/`, or `__tests__/` directory (`documentation/adr/0033`); `_test.go`; Maven's `src/test/` or `*Test.java`/`*Tests.java`; Cargo's top-level `tests/*.rs`; pytest's `test_*.py`/`*_test.py`, any file under a `test/` or `tests/` directory at any depth, or `conftest.py` at any directory level (`documentation/adr/0047`)) is excluded from the codemap entirely by default - it is never discovered, so it never becomes a File node in the first place. An explicit opt-in (`--include-tests` / `includeTests`) makes test files visible again, in which case they're excluded from domain clustering and placed in one dedicated `tests` Module shared across the whole codebase, regardless of folder or which production files it imports - a test file's domain is testing, not whatever it happens to test.
- A known JS/TS build-tooling config file (a closed set of recognized basenames immediately before `.config.<ext>`, or the older `.<tool>rc.<ext>` dotfile form, e.g. `eslint.config.js`, `vitest.config.ts` - never a bare `*.config.*` word match, since "config" is also an ordinary domain word) is excluded from domain clustering entirely, the same way a test file is - but unlike test files, it is not bucketed into a shared Module, since an unrelated `eslint.config.js` and `vitest.config.ts` have no more in common with each other than either has with any other file. Each is simply left with no Module label at all (`documentation/adr/0048`).
- A Module's name is derived from its member files' shared folder structure, not detected from file content and not declared by a human - falling back to its members' shared Package name (`documentation/adr/0041`) when folder structure alone isn't enough, e.g. a monorepo package whose own entrypoint files sit directly in its `src/` with no further subdirectory to name it after. That fallback requires the Module to genuinely be its Package's own root - every other Module the Package owns nested in a subdirectory beneath this one, not scattered sideways as an equally-deep peer - whenever the Package owns more than one Module at all (`documentation/adr/0050`, `documentation/adr/0054`, `documentation/adr/0055`): a Module that's merely one of several peer areas under the same Package, or that reached this point by scattering across too many child directories rather than having none, would otherwise claim the Package's name as if it stood for the Package as a whole, when in fact it's simply the Package's own direct files with every other Module genuinely nested beneath it that deserves that name. When the fallback isn't available, the Module's own deepest real directory segment is used in its place. A plain ordinal label (`Module <id>`) is itself a last resort: two or more Modules that collide all the way down to sharing nothing but the same real directory name - e.g. two genuinely separate communities that both happen to sit directly in `src/cli/` with no further subdirectory, and no honest Package name to fall back on either - are numbered against each other instead (`cli-1`, `cli-2`), since that's still more honest than an unrelated integer (`documentation/adr/0052`, `documentation/adr/0054`).

See [`documentation/LLD.md`'s `ModuleDetector` seam section](documentation/LLD.md#srcclusteringlouvain--the-moduledetector-seam) for the clustering thresholds and weighting that decide these boundaries, and its JSON `Transformer` section for the exact name-derivation rule, with the full ADR history behind each.

## Interaction

An edge between two Clusters, or between a Cluster and an External, representing a relationship discovered between them.

- **kind**: a discriminant on every Interaction, one of:
  - `static` - derived from source without running the code: an import between files, or a call between functions/methods. TS/JS extraction resolves these from the TypeScript Compiler API's type-checked AST; Go/Rust/Java/Python extraction resolves them syntactically (tree-sitter, no type checker) - a namespace/path-qualified reference resolves to its specific target, an unqualified one to every same-named candidate (`documentation/adr/0027`, `documentation/adr/0030`). The only kind produced so far.
  - `dynamic` - derived from observing the code actually run (a runtime-traced call). Not produced yet, but the schema carries this discriminant from day one so a dynamic-tracing layer can be added later without a breaking schema change. Never synthesized as a stand-in for an unresolvable cross-language relationship either (`documentation/adr/0027`) - a Go file calling into a Rust binary at runtime is simply absent from the graph, not guessed at.

## Output artifacts

A single generator run produces exactly two files describing the same underlying graph of Clusters and Interactions:

- **The map JSON**: the graph, machine-readable, meant for an AI coding agent (Claude Code, or any MCP client) to consume as context.
- **The map HTML**: a single, self-contained HTML file rendering the same graph as an interactive, filterable visualization, meant for a human to read. Self-contained means zero runtime network dependency, not just "one file": any third-party code the visualization needs is vendored/inlined into the file at generation time, never loaded from a CDN, so the file works fully offline.

## Filter

Narrows a graph along one of several facets: **path** (which Package/Directory/File; `.` is the whole repo, and a `<dir>@<family>` Package id narrows to that family's files, `documentation/adr/0034`), **symbol kind** (function, class, const, etc.), **free-text search** (matching names), and - HTML visualization only - **language** (typescript, javascript, go, rust, java, python). The first three apply to both the map HTML's visualization (a human narrowing what's on screen) and the MCP `read` tool (an agent narrowing what's returned) - the same three facets, the same meaning, on two different consumers of the same graph; `language` narrows only the HTML visualization, since it's derivable from `path`/`search` results already for a programmatic caller. When more than one facet is applied at once, they narrow together: a result must match all of them, not any one.
